# A/C 연동 확인사항

이 문서는 아직 결정되지 않은 연동 사항을 실제 계약처럼 확정하지 않기 위한 목록이다. 확정된 항목은 API 명세에 반영하고 여기에는 결정 결과와 날짜를 기록한다.

## 이미 정한 원칙

- B는 제공된 값의 형식과 명백한 범위를 검증한다.
- B는 결측값을 임의로 대치하지 않고 A에 `null`로 전달한다.
- A는 모델 학습과 일치하는 전처리 규칙으로 결측값을 보정한다.
- HMI용 공개 API는 예측과 최적화를 한 번에 요청한다.
- B 내부의 예측 책임과 최적화 책임은 분리한다.
- XAI는 MVP 이후의 선택 기능이며 현재 가짜 결과를 만들지 않는다.
- B가 공정 적용과 시작을 통제한다.
- MVP에서 Unity는 FastAPI의 명령을 주기적으로 조회하고 상태를 보고한다.
- B의 API는 특정 Unity 버전에 의존하지 않는다.

## A 담당자와 확인할 사항

1. 분석 요청에서 최소한 하나라도 반드시 있어야 하는 입력값은 무엇인가?
2. 각 입력 필드의 정확한 이름, 단위, 정상 범위는 무엇인가?
3. `null`을 허용하지 않는 필드가 있다면 무엇인가?
4. 결측값 대치 후 사용한 값을 결과에 함께 반환할 것인가?
5. 예측과 최적화를 Python 함수 호출로 연결할지 별도 HTTP 서비스로 연결할지?
6. 예측·최적화의 평균 및 최대 처리 시간은 어느 정도인가?
7. 실패 시 구분 가능한 오류 종류와 메시지는 무엇인가?
8. XAI를 추가할 경우 어떤 형식이 필요한가? 예: 변수 중요도, SHAP 값, 설명 문장.

## C 담당자와 확인할 사항

1. Unity가 표현할 공정 조건과 각 단위는 무엇인가?
2. 어떤 조건 변경이 어떤 설비·재질·애니메이션 변화로 이어지는가?
3. Unity가 보고할 상태와 진행률 정보는 무엇인가?
4. 명령 조회와 상태 보고 주기는 어느 정도가 적절한가?
5. Unity 종료·연결 끊김·명령 실패를 어떻게 구분할 것인가?
6. 최종 시연에 사용할 Unity 버전과 빌드 대상은 무엇인가?
7. 제공된 `.unitypackage`를 선택한 Unity 버전에서 정상적으로 가져올 수 있는가?

## 구현 과정에서 정할 항목

- 공정 조건의 최종 필드와 단위
- A/C 연결 주소와 실행 순서
- 태블릿과 시연 PC의 네트워크 환경
- Unity 폴링 주기
- 실제 A/C 연결 전환 기준
- XAI 개발 여부와 일정

## 2026-10-14 MVP 구현 메모

- 위 미확정 항목을 임의로 계약화하지 않고 `draft-1` 스키마와 모의 어댑터로 구현했다.
- 공정 조건을 HMI에서 Unity 명령 큐로 보내고 Unity가 조회하는 방향은 구현됐다.
- Unity 정확한 버전은 HTTP 계약과 분리되어 있어 Unity 5/6 결정 후에도 B API를 유지할 수 있다.
- 실제 연결 작업 전에는 A/C 담당자가 각 확인사항에 답하고 이 문서에 결정 날짜와 결과를 기록해야 한다.
